# Add clarification-respond to the ops a2a verb whitelist with boundary-validated bounded args (run id, request id, answers keyed by question id)

## Scope

- `engine/crates/vaultspec-api/src/routes/ops/a2a.rs`

## Description

- Add `clarification-respond` to the ops a2a pass-through verb whitelist (six verbs become seven) as the typed resume of a run parked on a clarification interrupt.
- Bound every argument at the engine boundary before any round-trip: run id and request id path-safe (both interpolate into the sibling URL), answers map one to four entries against the four-question ceiling, question ids bounded tokens, answer values single-line capped strings.
- Forward the answers body to the sibling route and return the a2a envelope verbatim inside the tiers envelope; a known-down sibling degrades the agent tier at 200 via the existing template path.
- The engine judges no answer content: option-id existence, per-question satisfaction, and required-question completeness remain the parked node's authority.

## Notes

Two lead-approved structural choices. First, the clarification boundary lives in its own module `engine/crates/vaultspec-api/src/routes/ops/a2a/clarification.rs` rather than growing the verb file past the module-size ceiling; the sibling-reconciling surface (route spelling and answers body key) is thereby one small file. Second, the gating reading: the verb is gated BY THE SIBLING, not by an engine feature flag - until a2a serves the route the forwarded call is a sibling 404 relayed verbatim, and the engine can never fabricate a resume; pinned by a dedicated inertness test. The upstream route was implemented from ADR D5 ahead of the a2a landing and reconciles against it when P03 commits.
